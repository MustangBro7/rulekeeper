01 — rulekeeper drift

A doc that describes a repo that no longer exists.

You renamed a script six weeks ago. Your CLAUDE.md still tells every agent to run the old one. They try, it fails, they improvise — and you pay for the detour in tokens and wrong turns. Drift is a static check: no logs, no network, safe in CI.

  • Dead paths. Files and directories the doc points at that aren't there anymore — including the ones buried in ASCII tree diagrams.
  • Phantom scripts. npm run typecheck in the doc, no typecheck in package.json. Suggests the closest real script.
  • Missing targets. Make targets, just recipes and cargo aliases that no longer resolve.
  • Stale examples. A code sample importing a package you removed from your dependencies.
  • Wrong package manager. The doc says pnpm; the lockfile says npm.
  • Contradictions. Root CLAUDE.md and nested AGENTS.md telling agents opposite things.
  • Undocumented territory. Source directories no instruction file has ever mentioned.

02 — rulekeeper adherence

A true doc that nobody ever read.

Drift proves the file is correct. It does not prove the file works. Adherence joins your rules with what Claude Code and Codex actually did — every command, every edit — and scores each rule with a session receipt you can open and read.

  • Delivery. Per session, did the instruction file reach the model's context at all? Most teams discover it usually didn't.
  • Adherence. Of the sessions that received a rule and could have obeyed it, how many did?
  • Dead weight. Rules followed just as reliably when they were not in context — your agents already did this. Delete the line, reclaim the tokens.
  • Receipts. Every violation carries a session id, a date and the concrete evidence.
  • Rule birthdays. Rules are dated from the git commit that introduced them, so sessions predating a rule are never counted against it.

the taxonomy

Nine ways a steering file goes wrong.

Each finding carries a severity, the exact line, what the repo actually looks like, and a fix when one is mechanically derivable.

ERROR

missing-path

The doc references src/handlers.ts. The repository has no such file.

ERROR

missing-script

npm run typecheck is documented; package.json defines check.

ERROR

missing-target

make deploy is documented; the Makefile has no such target.

WARN

missing-dependency

An example imports zod, which is not in any package.json.

WARN

unknown-env-var

DATABASE_URL is documented but never read by the code or declared in env files.

WARN

package-manager-mismatch

The doc mandates pnpm; the repo carries a package-lock.json.

WARN

contradiction

Two instruction files give agents conflicting instructions on the same subject.

NOTE

stale-section

A directory the doc describes has changed in 40 commits since the doc was last touched.

NOTE

undocumented-area

A source directory that no instruction file has ever mentioned.

the dashboard

One number that tells you whether your docs are rotting.

The CLI answers the question today. The dashboard answers it over time: connect a repository, drop in the Action, and every push records a truth score you can watch — with the findings, the fixes, and the commit that broke it.

  • Truth score over time. A line that trends down is a doc quietly drifting away from the code.
  • Every finding, triaged. Filter by severity, read the doc line and the repo's actual state side by side.
  • Accept what you meant. Some findings are intentional. Accept them once and they stop failing the build — everywhere, for everyone.
  • Run history. Branch, commit and score for every run, so you can point at exactly when it broke.
  • Free, and your code stays put. Reports are generated in your runner. We store counts, findings and quotes from your own docs — never your source.

continuous integrity

Fail the build when the doc stops being true.

drift belongs in CI next to your linter. The Action fails the build on errors, posts a summary comment on the pull request, and records the score on your dashboard. Findings you have accepted never fail anyone’s build again.

Read the docs ↗ 
# .github/workflows/rulekeeper.yml
name: agent-instructions
on: [push, pull_request]

jobs:
  drift:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - uses: MustangBro7/rulekeeper@v2
        with:
          token: ${{ secrets.RULEKEEPER_TOKEN }}

local by construction

Your code never leaves the machine.

Both checks run entirely locally. The only network call the CLI can make is an explicit rulekeeper share, and it refuses to send anything that fails its own redaction audit.

Zero runtime dependencies and no background calls. Read the source — it's a few thousand lines of plain TypeScript.
